# Квиз и заявка

## Квиз

- Квиз — `/<locale>/brief`, страница «спасибо» — `/<locale>/brief/thanks`.
- Верстка одна на пять направлений (`src/components/Brief/`), построена только на токенах → у каждого стиля своя палитра,
  шрифты и радиусы без отдельных реализаций. Артборда у квиза нет — на `design/*.dc.html` нарисована только главная.
- Миниатюры стилей на третьем шаге рисуются токенами чужого направления: блоки `[data-design='<name>']` лежат в общем CSS
  → атрибуты `data-design` и `data-theme` прямо на узле дают его палитру внутри текущего стиля. Настоящие шрифты
  направления в миниатюру не приезжают (они в его CSS-чанке) → миниатюра абстрактная, без текста.
- Ответы шагов — ключи справочников `BRIEF_STEP_VALUES` (`src/lib/brief/consts.ts`), а не переведенный текст: значение
  вне справочника на сервер не проходит.
- Продукты первого шага берутся из `PRICING_PLANS` → новый тариф появляется в квизе сам; `?plan=` с кнопки прайса
  предвыбирает первый шаг.

## Заявка

- Принимает `POST /api/brief` (`src/app/api/brief/route.ts`): лимит по адресу → разбор через `parseLead` → `deliverLead`
  в три канала параллельно: Telegram (по одному запросу на каждый id из `TELEGRAM_CHAT_IDS`), письмо через SMTP, лид
  в Bitrix24.
- Упавший канал не уносит остальные: ошибки собираются и пишутся в лог; 502 — только когда молчат все три.
- На сервере студии (Timeweb) исходящий SMTP закрыт хостингом (порты 25, 465, 587, 2525) → почтовый канал молчит,
  пока Timeweb не откроет порты или письмо не пойдет через HTTP-API почтового сервиса; заявки идут Telegram и Bitrix24,
  ошибка почты — только в логе. Открытый пункт блока B4 в `../ROADMAP.md`.
- Тексту заявки (`formatLead`) нужна нижняя часть с `ключ=значение` — по ней тесты и будущие отчеты находят источник,
  нишу, стиль и метки. Менять формат, не поправив `tests/unit/brief.test.ts`, нельзя.
- Метки кампании снимает `src/proxy.ts` и кладет в cookie `marks`: по рекламе приходят на главную, а заявку оставляют
  на брифе — к моменту отправки меток в адресе уже нет.
- Ловушка для ботов — поле `zone` (`HONEYPOT_FIELD`), спрятанное за экран. Имя нарочно вне словаря автозаполнения:
  на `company` браузер подставил бы организацию живому человеку, и его заявка молча пропала бы. Заполнена → ответ 200
  без единой отправки: по ответу бот не должен понимать, что его отбили.
- Без чекбокса согласия кнопка не нажимается, прямой запрос получает 422.

## Приемник заявок в e2e

- Заявка в e2e уходит в настоящие каналы, только приемник — `tests/e2e/lead-sink.ts`: HTTP-сервер для Telegram
  и Bitrix24 и настоящий SMTP-сервер для письма. Оба поднимаются третьим `webServer` в конфиге Playwright, адреса каналов
  подменяются через `LEAD_ENV` (ручной сервер для этих тестов не годится — `CLAUDE.md`).
- Письмо приходит закодированным → приемник раскодирует тело (base64 и quoted-printable), иначе вместо `source=site`
  в нем лежало бы `source=3Dsite`.
- Тесты отбирают свои записи по маркеру в имени заявки → параллельные прогоны друг другу не мешают.
- Лимит заявок живет в памяти сервера и переживает прогоны → спек квиза шлет свой `x-forwarded-for` на каждый запуск.
